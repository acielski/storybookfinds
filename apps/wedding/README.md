# Ever After · A personal wedding planner

An independent app alongside Storybook Finds. It has its own package, server, database, authentication storage key, Supabase tables, and Vercel configuration. It does not read or change pin-shop records.

[View the dashboard design](docs/preview.png) — screenshot from isolated sample data, not a prefilled real wedding plan.

## Start here

Requires Node 24. In a terminal:

```sh
cd /workspace/storybookfinds/apps/wedding
npm ci --cache /workspace/.npm-cache
npm run dev
```

The wedding app runs on **port 3100**. The pin shop can continue running on its own port. Open the wedding app in your development browser. Override the wedding port with `WEDDING_PORT` (or `PORT`).

The app starts with an empty wedding plan. Click **Our wedding details** to add your names, date, venue and budget. No fictional guests, expenses or wedding details are saved to the real app. Screenshots generated by browser tests use isolated test data.

## What is included

- **Overview:** wedding countdown, budget, guest count, checklist progress, next tasks, payment reminders and recent notes.
- **Budget & expenses:** category budgets, full booking costs, deposits, amounts already paid, outstanding amounts, due dates, vendor links and mark-paid actions. Committed costs are counted once; deposits do not create a second expense. Unallocated costs remain visible as Uncategorized. Over-budget totals are shown rather than hidden.
- **Checklist:** dates, assignees, categories, priorities, complete/reopen, search and filters.
- **Guest list:** people or households, party sizes, RSVPs, groups, contact details, tables/seating, dietary needs, notes and CSV export. Guest counts include everyone in each household.
- **Contacts:** vendors and other contacts, booking status, email, phone, website and notes. Quotes in contact notes do not count as expenses; add a booking in Budget & expenses.
- **Our notes:** ideas, journal entries, decisions and inspiration, with tags, paper colors, pins and full-text reading/editing.
- **Backup:** Download our backup exports the entire wedding plan as JSON. Keep this file private: it includes contact information and wedding finances. This release exports backups but does not have an import/restore screen.

CRUD controls require owner/editor access in cloud mode. Deleting a used budget category is blocked until its expenses are reassigned. Deleting a contact unlinks its expenses without removing their amounts. Saves use version checks so simultaneous changes cannot silently overwrite one another. On a conflict, the app reloads the latest plan and keeps the open form so you can retry.

All money is USD, stored as integer cents. Local date-only values are used for the wedding and planning dates. This is a planning and record-keeping app: it does not send invitations, make payments, or connect to a bank. Receipts and document uploads are not included.

## Storage and privacy

Without Supabase settings, the app uses its own `data/wedding.sqlite` in this folder. Override with `WEDDING_DB_PATH`. These files are excluded from Git. They persist across local server restarts. Local mode has no login and should remain inside a private development environment.

Vercel requires Supabase configuration and fails closed when it is missing; it never falls back to an ephemeral local database. Cloud mode uses Supabase login, a separate `wedding_plans` table, `wedding_members`, and wedding-specific database functions. All API requests verify the Supabase session. Row-level policies isolate unrelated users. No privileged/service-role key is needed. The original pin app's tables and membership settings are not used.

## Deploy as a separate app

Do not change the existing Storybook Finds Vercel project's root directory or database settings.

1. Choose the Git branch containing `apps/wedding` (initially `dev`). The folder must exist on the branch you deploy.
2. Create a new Supabase project for the wedding app, for example `ever-after-wedding-dev`. Run `supabase/001_wedding.sql` in its SQL Editor. It is safe to rerun.
3. Create your wedding app login under **Authentication → Users → Add user → Create new user**, with Auto Confirm enabled. Disable public signup and keep Email sign-in enabled.
4. Create a **new Vercel project** connected to this repository and branch. Set **Root Directory** to `apps/wedding`, framework to **Vite**, Node to **24.x**, build command to `npm run build`, and output directory to `dist`.
5. In that new project's environment settings add `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` from the wedding Supabase project. Do not use a secret/service-role key or database password. For a development site, optionally add `APP_ENV=development`.
6. Deploy and sign in using the wedding app user's email and password. A new cloud plan starts empty; local SQLite data is not uploaded automatically.
7. For a production wedding site later, use separate production Supabase and Vercel settings. Do not point a test site at a database containing real wedding or contact details.

If you test Supabase locally, copy `.env.example` to `.env.local` inside this folder and enter the two settings there, then restart. Do not copy credentials from another app's environment file.

## Share with your partner

Create your partner's separate account in the **wedding** Supabase project's Authentication → Users section. In `supabase/add_partner.sql`, replace `OWNER_EMAIL` and `PARTNER_EMAIL` with the two existing app login emails. Run it as an administrator in that project's SQL Editor. Both people can then see and edit the owner's same wedding plan. No records are copied or merged with the pin shop.

Membership is managed in Supabase for now. Change `role` to `viewer` in `wedding_members` for read-only access, or delete the membership to revoke access. The owner and assigned partner can read the shared plan; unrelated accounts cannot. There is no public signup or email-invitation screen in this app.

## Validate

```sh
npm run build
npm test
npm run test:browser
```

The browser checks use a temporary, empty in-memory database and a test authentication provider. They never read or overwrite the real wedding database. They use system Chromium when available, or Playwright's browser installation; `CHROMIUM_PATH` can select an installed Chrome/Chromium executable. On a new machine without Chromium, install the Playwright browser using its documented installer before running browser checks.

Checks are under `checks/*.spec.mjs` and explicit browser scripts, so the pin app's default `node --test` discovery does not run wedding tests accidentally. Live Supabase/Vercel validation still requires configuring those services yourself; local tests do not publish a site.
